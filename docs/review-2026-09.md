## Project intent used to judge findings

- A companion to the built-in SmartThings integration: no extra login, token or IP.
- Safety first: assumed state, no startup commands, never replay a POST, never guess.
- Prepared for public HACS distribution; nothing is published yet.
- HW-Q930D is the only profiled and physically tested model.
- The v1 → v2 migration existed for the author's own install, which was migrated on
  2026-09-05. No other v1 installs are known.

## Findings

Priority is for the public release. "Original" is the first-pass review; "Decision"
is the result after checking project intent and live state.

### 1. Validate the next-source button on the device — high

`smartthings.py` only counts `COMPLETED` as success. That is proven for `execute`
(v1 and v2 both required it in production). `setNextInputSource` is a different
capability, and the live logbook shows the button has never been pressed. If Samsung
answers `ACCEPTED`, the user sees an error for a command that worked, presses again,
and skips past the input they wanted.

**Decision:** don't relax the check on speculation. Press the button once on the real
soundbar and record the response. If it is `ACCEPTED`, accept it for that capability
only. Keep `execute` strict.

### 2. Missing `CONFIG_SCHEMA` — high, one line

`__init__.py` defines `async_setup` without a `CONFIG_SCHEMA`. hassfest is expected to
reject this (not confirmed locally), and hassfest runs in `validate.yml` for HACS
publication. Add `CONFIG_SCHEMA = cv.config_entry_only_config_schema(DOMAIN)`.

Pinning GitHub Actions to commit SHAs is good hygiene but lower priority: the
workflows already run with `contents: read`.

### 3. Test the SmartThings boundary with real types — medium (downgraded)

Tests model the parent's `runtime_data`, devices and events with `SimpleNamespace`,
and `pysmartthings` is not installed in the test venv.

**Checked:** the example risk is not a bug. `pysmartthings.HealthStatus` is a
`StrEnum` (`ONLINE`, `OFFLINE`, `UNHEALTHY`), so `str(event.status)` works. The live
integration runs correctly against the real parent: the entities are available and the
source sensor reports `D.IN`.

**Decision:** keep a smaller version. Add the `pysmartthings` version pinned by HA's
SmartThings manifest (4.0.1 on 2026.9) to `requirements_test.txt`, and build the
fixtures from real `FullDevice`, `SmartThingsData` and `DeviceHealthEvent`. That
catches drift when HA updates the library. The README already says this boundary must
be checked on HA upgrades. Skip the HA version matrix for now (YAGNI).

### 4. Deleted SmartThings entry leaves the companion stuck — medium (adjusted)

Each entry stores `parent_entry_id`. If SmartThings is deleted and re-added, the
companion stays in `SETUP_RETRY` forever with the message "not loaded".

**Decision:** don't find the parent by `device_id` instead. Re-adding SmartThings is
rare, the README documents the fix, and rebinding the parent state-change hook adds
lifecycle complexity. Instead, tell the two cases apart:

- Parent entry missing → `ConfigEntryError` with "remove and re-add this soundbar".
- Parent entry present but not loaded → `ConfigEntryNotReady`, as now.

### 5. Refactors — low

Accepted:

- `SmartThingsAdapter.has_capability(cap)`. `button.py`, `sensor.py` and
  `diagnostics.py` read `adapter.device.status["main"]` directly, which breaks the
  README's claim that `smartthings.py` is the only code coupled to the parent.
- One `runtime.enabled(key)` helper (`key in settings and key in
  available_controls(model)`) used by the platforms and `runtime.py`. Keep the check
  inside `runtime.py` as defense in depth, because the legacy `set` action bypasses
  the entities.
- Merge the repeated lock → availability → command → store → notify code in
  `runtime.py` into one method.
- ~~`via_device=("smartthings", device_id)` instead of `via_device_id`.~~ **Withdrawn.**
  The review got this backwards: in HA 2026.9, `via_device` is deprecated (removal in
  2027.8.0), and `via_device_id` is the typed replacement. The current code is correct.

### 6. v1 migration hardening — rejected; consider removing it

The first-pass review found three problems in the v1 migration:

- It moves the three template switches one at a time, so it can half-finish.
- It uses `ConfigEntryNotReady` for a condition that needs the user to act.
- `async_migrate_entry` fails permanently if SmartThings isn't loaded yet.

**Decision:** don't harden it. The only known v1 install was migrated on 2026-09-05,
and v1 was never distributed. Hardening code that no user will run is YAGNI.

**Resolved:** the owner confirmed v1 was never shared, so the v1 path was removed:

- the `version == 1` branch of `async_migrate_entry`
- the `migrate_legacy` block in `async_setup_entry`
- `LEGACY_SWITCHES`
- `scripts/prepare_migration.py`
- `docs/migration.md` and its tests

Keep the `minor_version < 2` step. It upgrades v2.0 entries.

## Kept as-is (confirmed intentional)

- A direct POST instead of `client.execute_device_command`. That method returns
  `None`, so it can't check `results[].status`. The acceptance check is the reason
  for the separate POST.
- Assumed state for every advanced control. Live read probes return null.
- The legacy `soundbar_control.set` action with a raw SmartThings device ID. It exists
  for compatibility; the switch entities are the recommended path.

## Security

No blocking issues. The token only exists inside one request header and is never
logged or stored. Diagnostics use an allowlist, and a test checks they leak nothing.
The service's `device_id` is only compared, never put into the URL. Level input
rejects NaN, infinity, booleans and fractions. The migration script (since removed) used the safe
YAML loader, refuses to overwrite an existing file (`open("x")`) and writes the result
owner-readable only (0600). `.local/` (configuration backups, rollback archives) is
gitignored and not in the `dist/` zip.

## Found after deployment (2026-09-23)

Found after the first deploy. Night mode, voice amplifier, bass boost and sound mode
came back `unknown` after a restart. The speaker levels were kept. Two bugs from
v2.0 combined:

1. **Stale availability at setup.** `bind()` started from the parent's
   `FullDevice.online`. SmartThings sets that flag only during its own setup and
   never updates it. SmartThings reloaded at 01:08 while the soundbar was offline;
   the companion was reloaded at 09:06, started from that stale `False`, and stayed
   unavailable. **Fix:** after each bind, read `GET /v1/devices/{id}/health` once in
   an entry background task, so unload cancels it. A version counter makes any newer
   health event or rebind win over a slow read. A failed read keeps the snapshot.
   Still no polling.
2. **Values lost when unavailable at shutdown.** Switches and the sound-mode select
   restored from the saved state text, which was `unavailable`. Numbers kept their
   values because `RestoreNumber` saves `native_value` separately. **Fix:**
   `RestoredAssumedEntity` saves the assumed value as extra restore data
   (`assumed_value`). It falls back to the state text so values saved by older
   versions still restore, and validates both.

`tests/test_resilience.py` covers both. Run against the old restore code, the
restore tests fail exactly as the live install did. 57 tests pass, 97% coverage.
Deployed; takes effect at the next restart. Rollback:
`.local/rollback-resilience.bak.20260923.tar.gz`.
